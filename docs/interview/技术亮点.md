# FitAgent 技术亮点

## 亮点一：可解释的混合 RAG 与结构化意图路由

**设计**：把明确的通用健身知识问题从完整 Agent 中分流，走一次受控的 RAG 编排与一次回答生成；个性化问题才进入 LangGraph ReAct。普通问题保持单查询，指代或复合问题最多扩展为两个子查询。

**实现要点**：

- Qdrant revision collection + `rag_active` alias，新 collection 写入后的向量数量校验通过才切换，在线永远只读；BM25 工件与活动向量 revision 不一致时降级为 Dense，避免混用版本；
- `StateGraph` 通过 Pydantic 约束的结构化 `IntentDecision` 路由：仅明确的通用知识进入 Direct RAG，个性化、模糊、超时或校验失败统一回退到个性化 Agent；
- `ChatRuntimeContext` 只保存身份、城市和执行依赖，`ChatGraphState` 只保存 JSON 安全的会话事实、检索历史、证据、预算与事件；官方 Collector 由 HTTP 层经 `RunnableConfig.callbacks` 注入，两者不互相污染；
- 查询规划只在指代/复合问题时调用模型，最多保留两个子查询；
- 混合召回后做去重、轻量词法重排和上下文预算；SSE 同时传文本、工具进度与由检索结果生成的结构化证据卡片，证据卡片不依赖反解析模型回答。

**价值**：在不牺牲证据可追溯性的前提下，避免所有问题都承担 Agent 多轮决策的延迟和不确定性；同时避免关键词边界漂移，并使分类失败有保守、安全的落点。

**当前边界**：聊天回答中的 `[证据:N]` 由 Prompt 约束，尚未做生成后白名单校验；训练计划的 `evidence_ids` 已有服务端校验。

## 亮点二：用户可控的三层记忆，而不是全文向量化

**问题**：健康、伤病和偏好信息一旦被模型错误长期化，可能造成隐私和安全问题。旧实现还会从 assistant 消息中抽取事实，存在模型“自我污染”风险。

**设计**：

| 层 | 实现 | 规则 |
|---|---|---|
| 近期会话 | 最近 10 轮（20 条）原文 | 保持对话连贯性 |
| 短期状态 | `session_summaries` | 只从较早用户消息确定性提取，可重建，不替代原文 |
| 长期记忆 | mem0 主向量库正文与元数据 | LLM 提取为 `proposed`，用户确认或撤销，来源与有效期可查 |

**实现要点**：assistant/tool 消息不进入提取输入；mem0 用 LLM 从用户消息提取候选；模型自主决定是否调用查询工具并组织 query，通过向量检索召回已确认且未过期的记忆，默认最多 6 条。冲突候选由用户审核并自行撤销旧值。MySQL 保留完整聊天与业务数据，旧 `memory_facts` 仅供显式迁移；mem0 SQLite 的最近 10 条提取上下文不替代完整聊天。详见 [记忆架构](../memory-architecture.md)。

**价值**：把“模型猜到的信息”和“用户授权的长期事实”分开，使个性化可解释、可撤销且能单测。

## 亮点三：训练计划的双重约束——确定性安全策略 + 结构化生成

**设计**：训练计划不只是一段自然语言 prompt。`TrainingSafetyPolicy` 先基于画像、近四周聚合快照和最近反馈得出最大强度，LLM 再输出 `WeeklyTrainingPlan` JSON。

**安全降级信号**：伤病/不适、训练负荷比 > 1.3、平均睡眠 < 6 小时、疲劳度高、疼痛评分 ≥ 4、极高 RPE。

**服务端门禁**：

- 7 天完整覆盖且没有重复星期；
- 训练日不得超过用户 `weekly_days`；
- 每个动作强度不得超过策略上限；
- `evidence_ids` 必须来自本次 RAG 命中；
- 任一失败不写入计划，反馈按 `(plan_id, day_of_week)` 幂等更新。

**价值**：将生成模型的概率性行为与业务安全门禁解耦，便于审计、回归测试和面试说明。

## 工程支撑：Coros MCP 的可靠性与数据幂等修复

> COROS 接入不是本项目的第四个核心产品亮点；它为“自适应训练计划”提供真实、受控的运动数据输入，并展示外部协议适配与数据可靠性能力。

**问题**：旧实现使用 Windows 不支持的 `select.select(pipe)`，并发共享 stdio JSON-RPC 流会造成回包交叉；活动按日期唯一会覆盖同日晨跑/夜跑。

**实现**：

- 整个“发送请求—等匹配回包”持有可重入锁；
- reader thread + queue 提供跨平台超时；超时/断管立即终止进程，下一次调用重建；
- `COROS_MCP_COMMAND` 配置化并支持 Windows 路径 JSON argv；
- 社区 `coros-mcp` 固定到独立 `.tools` 虚拟环境，避免 FastMCP 传递依赖升级 FastAPI 服务的 Starlette；适配器强制 `readonly` 并隐藏认证工具；
- 发现社区包将缓存硬编码在用户目录且与本机文件冲突后，增加隔离解释器 Runner，在导入 provider 前仅重定向 SQLite cache，不改动 Windows Credential Manager 的令牌路径；同步作为显式 API 步骤，聊天 Agent 无权触发；
- 显式同步拥有数据刷新权，读取 MCP 只消费缓存；正常的睡眠空数组仍视为完整成功，只有睡眠等单一源明确不可用时才采用 `partial + unavailable_sources` 契约，让日指标/活动继续落库而不是整次事务回滚；
- `fitness_data` 以 `(user_id, data_type, external_id)` 唯一：活动优先取上游 ID，缺失时用稳定字段哈希兜底；迁移先创建新索引以兼容 MySQL 外键。
- Agent 不读取原始 Coros 载荷：运动数据工具默认返回近四周摘要，也只允许在最多 90 天的指定区间聚合；若要分析同日某次活动，必须先获取候选活动，再以稳定 `external_id` 精确读取白名单指标。

**价值**：MCP 被当作外部适配器而不是“接上协议就可靠”，可稳定验证同日多活动和超时恢复。

## 工程支撑：可观测、可测试、可演示的 AI 工程闭环

- Agent 运行记录使用官方 `RunCollectorCallbackHandler` 在内存采集，SSE 结束后投影到既有本地 MySQL `agent_runs`、`agent_tool_calls`，保存用户问题、最终回答、工具输入、输出与耗时；不使用 LangSmith，也不新增表或路由；
- 外部依赖通过 FastAPI 依赖注入，可用 mock 覆盖，不需要真启 Coros 或真调 LLM；
- ruff + pytest + 前端 build 是基础门禁；关键测试覆盖记忆污染、计划越界、虚构证据、Coros 握手/超时、同日多活动；
- README、架构、决策、API 契约、执行计划和演示脚本与代码一同维护。

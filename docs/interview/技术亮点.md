# FitAgent 技术亮点

## 亮点一：可解释的混合 RAG 与结构化意图路由

**设计**：把明确的通用健身知识问题从完整 Agent 中分流，走一次 Qdrant 原生混合检索、一次 DashScope 二阶段排序与一次回答生成；个性化问题才进入 LangGraph ReAct。RAG 全程保持单次 Qdrant 查询，应用层只在上下文预算内组织最终证据。

**实现要点**：

- 知识库只有 `fitagent_knowledge` 一个 Qdrant collection，包含命名为 `dense` 的语义向量和命名为 `sparse` 的 Qdrant 原生 BM25 向量；离线索引器规范化文档、切片并写入两种向量；
- 每次检索只发起一次 Qdrant Query API 请求：服务端分别 prefetch Dense 与 BM25 候选，再用 RRF 融合取 Top-30；索引数据和融合逻辑都由 Qdrant 管理；
- 应用层把用户问题与最多 30 个已召回候选交给 DashScope `gte-rerank-v2`，以 `return_documents=false` 接收索引和相关度，选出最终 Top-6，避免将模型重排分数与 Qdrant 分数混用；
- `StateGraph` 通过 Pydantic 约束的结构化 `IntentDecision` 路由：仅明确的通用知识进入 Direct RAG，个性化、模糊、超时或校验失败统一回退到个性化 Agent；
- `ChatRuntimeContext` 只保存可信请求身份和执行依赖，**没有 city 字段**；`ChatGraphState` 只保存 JSON 安全的原始消息、路由、检索产物、工具计数和 SSE 事件；分类器至多见最新 6 条规范化消息，个性化 Agent 才接收最新 20 条原始消息；官方 Collector 由 HTTP 层经 `RunnableConfig.callbacks` 注入，两者不互相污染；
- RAG 服务只把最终命中收敛为 source、chunk 和 score 等最小检索契约，再在上下文预算内构造证据；SSE 同时传文本、工具进度与由检索结果生成的结构化证据卡片，证据卡片不依赖反解析模型回答。

**价值**：在不牺牲证据可追溯性的前提下，避免所有问题都承担 Agent 多轮决策的延迟和不确定性；同时将混合检索的融合逻辑交给 Qdrant、用专用重排模型提高最终证据精度，并使分类失败有保守、安全的落点。

**当前边界**：聊天回答中的 `[证据:N]` 由 Prompt 约束，尚未做生成后白名单校验；训练计划的 `evidence_ids` 已有服务端校验。

## 亮点二：用户可控的三层记忆，而不是全文向量化

**问题**：健康、伤病和偏好信息一旦被模型错误长期化，可能造成隐私和安全问题。旧实现还会从 assistant 消息中抽取事实，存在模型“自我污染”风险。

**设计**：

| 层级 | 载体 | 进入模型的方式 |
| --- | --- | --- |
| 近期会话 | 当前会话最近 20 条原始消息 | 个性化 Agent 初始上下文；分类器仅见最新 6 条 |
| 早期会话背景 | MySQL session_summaries v3 缓存 | 当前窗口不足以解释早期引用时，Agent 按需调用 get_session_summary；压缩早期全部已存储消息，不是长期记忆 |
| 长期记忆 | mem0 | 用户消息提取为 proposed；模型按需调用 get_confirmed_memories(query)，只读 confirmed、未过期结果 |

**实现要点**：`session_summaries` 是 LLM 生成、可再生成的 v3 缓存：仅在 Agent 按需调用时压缩早期全部已存储消息（不按角色过滤），最近 20 条原始消息仍直接传入个性化 Agent；从不每轮预先生成、不写入 mem0，且仅由个性化 Agent 调用。模型结合当前系统提示词、最近消息和早期摘要综合判断。assistant/tool 消息不进入 mem0 提取输入；mem0 用 LLM 从用户消息提取候选，用户审核 proposed 候选并确认或撤销。天气必须从当前窗口或会话摘要取得明确城市，缺失就追问，不能编造。MySQL 保留完整聊天与业务数据，旧 `memory_facts` 仅供显式迁移；mem0 SQLite 的最近 10 条提取上下文不替代完整聊天。详见 [记忆架构](../memory-architecture.md)。

**价值**：把“模型猜到的信息”和“用户授权的长期事实”分开，使个性化可解释、可撤销且能单测。

## 亮点三：训练计划的双重约束——确定性安全策略 + 结构化生成

**设计**：训练计划不只是一段自然语言 prompt。`TrainingSafetyPolicy` 先基于画像、近四周聚合快照和最近反馈得出最大强度，LLM 再输出 `WeeklyTrainingPlan` JSON。

**安全降级信号**：伤病/不适、训练负荷比 > 1.3、平均睡眠 < 6 小时、疲劳度高、疼痛评分 ≥ 4、极高 RPE。

**服务端门禁**：

- 7 天完整覆盖且没有重复星期；
- 训练日不得超过用户 `weekly_days`；
- 每个动作强度不得超过策略上限；
- `evidence_ids` 必须来自本次 RAG 命中；
- 任一失败不写入计划，反馈按 `(plan_id, day_of_week)` 幂等更新。

**价值**：将生成模型的概率性行为与业务安全门禁解耦，便于审计、回归测试和面试说明。

## 工程支撑：官方 COROS MCP 的实时、安全接入

> COROS 接入不是本项目的第四个核心产品亮点；它为“自适应训练计划”提供真实、受控的运动数据输入，并展示外部协议适配与数据可靠性能力。

**问题**：官方 COROS 提供的是浏览器 OAuth + HTTP MCP，而不是可供多用户服务端直接共享的本地账号。若把 token、Adapter、工具目录或运动数据缓存到全局对象，会造成串户、越权或陈旧数据风险。

**实现**：

- OAuth 采用动态 client 注册、PKCE S256、短期 state hash 与一次性回调；access/refresh token、PKCE verifier 仅以 Fernet 密文存储，且不进入日志或 Agent state；
- 每一请求按当前 FitAgent 用户创建独立的 streamable HTTP MCP session，保存区域 issuer，但不共享 token、Adapter、连接或响应；401 只刷新并重试一次；
- Gateway 仅允许 `querySportRecords`、`queryDailyHealthData`、`querySleepData`，并在用户选择同日候选活动后才允许 `getActivityDetail`；工具目录及日期 schema 不兼容则拒绝读取；
- 返回载荷立即裁剪为 `LiveFitnessData` 和 `FitnessSnapshot`；没有 `fitness_data` 表、后台同步、缓存或原始运动数据落库；
- 单源失败返回 `partial + unavailable_sources`，全部失败则返回上游不可用；已连接用户的训练计划要求完整近四周快照，不能静默退回陈旧或不完整数据。

**价值**：MCP 被当作受控的用户级外部适配器，而不是“接上协议就可靠”；认证、权限、最小化数据与失败语义都落在明确的边界内。

## 工程支撑：可观测、可测试、可演示的 AI 工程闭环

- Agent 运行记录使用官方 `RunCollectorCallbackHandler` 在内存采集，SSE 结束后投影到既有本地 MySQL `agent_runs`、`agent_tool_calls`，保存用户问题、最终回答、工具输入、输出与耗时；不使用 LangSmith，也不新增表或路由；
- 外部依赖通过 FastAPI 依赖注入，可用 mock 覆盖，不需要真连 COROS 或真调 LLM；
- ruff + pytest + 前端 build 是基础门禁；关键测试覆盖记忆污染、计划越界、虚构证据、COROS OAuth 加密/重放、白名单和局部失败；
- README、架构、决策、API 契约、执行计划和演示脚本与代码一同维护。

# FitAgent 常见面试题

## 1. 这个项目解决了什么问题？

FitAgent 是一个面向个人健身场景的智能教练应用。它通过可解释 RAG 为训练建议提供可追溯的知识来源；用户的目标、伤病和偏好只有在本人确认后才会作为长期记忆使用，并且可以随时撤销。系统再结合用户画像、近期运动数据和训练反馈，生成受安全规则约束、会随身体状态调整的个性化训练计划。

## 2. 为什么通用问题不全部走 Agent？

明确的通用知识只需要检索证据与一次生成。完整 Agent 会多一次或多次模型工具决策，增加延迟、token 成本和非确定性，因此项目用 `StateGraph` 中的结构化 LLM 分类来分流。分类器至多读取最新 6 条规范化 user/assistant 消息；涉及画像、训练记录、天气、报告、意图模糊、超时或校验失败时都保守进入个性化 Agent，而不是依赖关键词。天气必须有当前窗口或会话摘要中的明确城市，否则 Agent 先追问，绝不编造城市。

## 3. 为什么使用 Dense + BM25 + RRF？

Dense 对语义改写鲁棒，BM25 对动作名、数值和术语更精确。两者分数尺度不同，不能直接相加，所以按排名用 RRF 融合。知识库在同一个 `fitagent_knowledge` collection 中保存命名 `dense` 和 `sparse` 向量；`sparse` 由 Qdrant 的 `Qdrant/bm25` 文档模型生成。每次查询由一次 Qdrant Query API 请求完成 Dense 与 BM25 prefetch 和服务端 RRF 融合，应用层不额外维护检索索引数据。

## 4. RAG 如何做到可解释？

离线知识源经规范化和切片后写入单一 collection；在线命中保留 source、chunk/evidence id 和最终 score。SSE 直接携带由 `RetrievalResult` 生成的结构化证据卡片，不从模型自然语言倒推引用。模型被提示在采用资料时保留 `[证据:N]`，但聊天文本尚未做生成后的证据 ID 白名单校验；训练计划的 `evidence_ids` 则有服务端校验。可解释不等于绝对正确，因此仍保留医疗边界和忠实度评测计划。

## 5. 这是 Agentic RAG 项目吗？

在宽泛定义下是，但更准确地说是**受约束的混合型 Agentic RAG**：`StateGraph` 先以结构化分类决定 Direct RAG 或个性化 Agent；后者才自主组合 `rag_summarize`、画像、记忆、会话摘要和运动数据等工具。GraphState 只保存原始消息、路由、检索产物、工具计数和 SSE 事件；`ChatRuntimeContext` 只保存可信请求身份与依赖，**没有 city 字段**；custom stream 再适配为既有 SSE。RAG 检索本身不是 Agent：它只向 Qdrant 发起一次 Dense + BM25 + RRF 查询以获得候选，再由 DashScope 重排最终命中并转换为最小证据契约。

## 6. 你的 Agent 是什么范式？如何防循环？

采用单 Agent ReAct：模型决定是否读取 RAG、画像、记忆、早期会话摘要、运动摘要等工具，工具结果再作为观察返回。只有个性化 Agent 能在当前窗口不足以解释早期引用时调用 `get_session_summary`。LangGraph recursion limit 和 middleware 工具预算双重限制；外部工具还有重试、熔断与降级。没有为了概念而上多 Agent。

## 7. 记忆为什么不直接向量化所有聊天记录？

健身目标、伤病和偏好属于高风险个人信息，向量化全文会带来检索错配、撤销困难和模型幻觉长期化。这里区分短期原文、可重建摘要和用户确认的长期记忆；只有 `confirmed` 且未过期项能被 `get_confirmed_memories(query)` 读出并进入 Agent。

## 8. 如何防止模型自己写入虚构记忆？

mem0 候选提取只接收 `role=user` 的消息，聊天写入路径只会生成 `proposed`。assistant/tool 文本完全忽略；确认动作只能从用户 API 发起。对应测试直接构造 assistant 声称城市/伤病的场景，断言不会生成候选。

## 9. 长会话如何控制上下文？

| 层级 | 载体 | 进入模型的方式 |
| --- | --- | --- |
| 近期会话 | 当前会话最近 20 条原始消息 | 个性化 Agent 初始上下文；分类器仅见最新 6 条 |
| 早期会话背景 | MySQL session_summaries v3 缓存 | 当前窗口不足以解释早期引用时，Agent 按需调用 get_session_summary；压缩早期全部已存储消息，不是长期记忆 |
| 长期记忆 | mem0 | 用户消息提取为 proposed；模型按需调用 get_confirmed_memories(query)，只读 confirmed、未过期结果 |

`session_summaries` 是 LLM 生成、可再生成的 v3 缓存：仅在按需调用时压缩早期全部已存储消息（不按角色过滤），绝不每轮预先生成；只有个性化 Agent 可在需要时调用它。模型结合当前系统提示词、最近消息和早期摘要综合判断。原始消息仍保存在 MySQL，不以摘要覆盖审计记录；摘要不写入 mem0，也不改变 mem0 的候选、确认或检索规则。

## 10. 为什么训练计划不能只写在 Prompt 里？

Prompt 只改变模型概率，不能保证安全。后端先根据伤病、负荷比、睡眠、疲劳、疼痛/RPE 计算最高强度，再验证模型 JSON 的星期覆盖、训练日数、动作强度和证据 ID；失败不落库。

## 11. 如何保证计划中的 RAG 证据没有幻觉？

RAG 服务返回本次可用 evidence id 列表，模型 prompt 限制只能引用该列表，服务层二次验证 `evidence_ids` 是其子集。模型给出任意其他 ID 就报错并不创建计划。

## 12. 官方 COROS MCP 如何避免用户间 token 和工具权限串用？

浏览器 OAuth 使用短期 `state` 与 PKCE verifier；数据库只存 state hash、加密 verifier，以及按 FitAgent `user_id` 关联的加密 access/refresh token 和区域 issuer。每次读取都从当前用户连接记录构造一个新的 HTTP MCP session，绝不跨用户复用 token、Adapter 或响应。

Gateway 不把 MCP 工具直接暴露给 Agent，而是固定白名单：日健康、睡眠、活动；活动详情还必须先验证为当天实时返回的候选 ID。它会验证工具目录和日期参数 schema，拒绝未知工具或无法限制日期范围的契约。

## 13. 为什么不再把 COROS 数据同步到 MySQL？

运动数据在请求期间标准化为最小快照，返回 Dashboard、Agent 或训练计划后即释放；MySQL 只保存用户自己的 OAuth 连接。这样避免缓存陈旧、同步任务和原始健康数据长期留存。代价是读取依赖实时上游：单源失败会在 Dashboard 中标记 `partial`，训练计划遇到任何不完整快照都会拒绝生成。

## 14. 如何测试没有真实 LLM 或 COROS 的部分？

FastAPI 通过依赖覆盖替换 Agent；OAuth 使用假的 discovery/DCR/token 响应验证 state、PKCE 与加密存储；Gateway 用假的 HTTP session 与工具验证白名单、逐用户凭据、局部失败和全源失败。训练计划服务的安全策略和 schema 校验仍可直接构造画像、快照、反馈和计划。

## 15. 目前有哪些真实不足？

路由已使用结构化 LLM 分类，但分类质量仍需离线评测和线上观测；聊天文本的 `[证据:N]` 尚未做生成后白名单校验。计划生成的质量还没有人工偏好/忠实度评测；COROS 的 HTTPS callback、动态注册策略、真实工具参数/字段 schema 与长期失败率仍需在预发测试账号上验证；Qdrant 是单节点演示。这些会按真实问题和评测结果再演进，而不是直接堆 cross-encoder、多 Agent 或设备自动下发。

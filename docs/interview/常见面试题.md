# FitAgent 常见面试题

## 1. 这个项目解决了什么问题？

FitAgent 是一个面向个人健身场景的智能教练应用。它通过可解释 RAG 为训练建议提供可追溯的知识来源；用户的目标、伤病和偏好只有在本人确认后才会作为长期记忆使用，并且可以随时撤销。系统再结合用户画像、近期运动数据和训练反馈，生成受安全规则约束、会随身体状态调整的个性化训练计划。

## 2. 为什么通用问题不全部走 Agent？

明确的通用知识只需要检索证据与一次生成。完整 Agent 会多一次或多次模型工具决策，增加延迟、token 成本和非确定性，因此项目用 `StateGraph` 中的结构化 LLM 分类来分流。分类结果受 Pydantic 枚举约束；涉及画像、训练记录、天气、报告、意图模糊、超时或校验失败时都保守进入个性化 Agent，而不是依赖关键词。

## 3. 为什么使用 Dense + BM25 + RRF？

Dense 对语义改写鲁棒，BM25 对动作名、数值和术语更精确。两者分数尺度不同，不能直接相加，所以按排名用 RRF 融合。离线构建 BM25 工件并和 Qdrant revision 对齐，避免索引版本不一致。

## 4. RAG 如何做到可解释？

离线知识源有 revision，在线命中有 source、chunk/evidence id；SSE 直接携带由 `RetrievalResult` 生成的结构化证据卡片，不从模型自然语言倒推引用。模型被提示在采用资料时保留 `[证据:N]`，但聊天文本尚未做生成后的证据 ID 白名单校验；训练计划的 `evidence_ids` 则有服务端校验。可解释不等于绝对正确，因此仍保留医疗边界和忠实度评测计划。

## 5. 这是 Agentic RAG 项目吗？

在宽泛定义下是，但更准确地说是**受约束的混合型 Agentic RAG**：`StateGraph` 先以结构化分类决定 Direct RAG 或个性化 Agent；后者才自主组合 `rag_summarize`、画像、记忆和运动数据等工具。请求身份和依赖只在 `ChatRuntimeContext`，短期 JSON 状态只在图内；custom stream 再适配为既有 SSE。RAG 内部的查询规划、混合召回和重排仍是受控检索流水线，不等同于 Agent。

## 6. 你的 Agent 是什么范式？如何防循环？

采用单 Agent ReAct：模型决定是否读取 RAG、画像、记忆、运动摘要等工具，工具结果再作为观察返回。LangGraph recursion limit 和 middleware 工具预算双重限制；外部工具还有重试、熔断与降级。没有为了概念而上多 Agent。

## 7. 记忆为什么不直接向量化所有聊天记录？

健身目标、伤病和偏好属于高风险个人信息，向量化全文会带来检索错配、撤销困难和模型幻觉长期化。这里区分短期原文、可重建摘要和用户确认的长期事实；只有 confirmed 且未过期项能进入 Agent。

## 8. 如何防止模型自己写入虚构记忆？

事实提取器只接收 `role=user` 的消息，聊天写入路径只会生成 `proposed`。assistant/tool 文本完全忽略；确认动作只能从用户 API 发起。对应测试直接构造 assistant 声称城市/伤病的场景，断言不会生成事实。

## 9. 长会话如何控制上下文？

保留最近 10 轮（20 条）原始消息保证连贯性，较早用户表达用确定性会话状态摘要承载；原始消息仍存在数据库，不以摘要覆盖审计记录。当前没有宣称 LLM 自动摘要，后续若要引入需要 schema、评测和冲突处理。

## 10. 为什么训练计划不能只写在 Prompt 里？

Prompt 只改变模型概率，不能保证安全。后端先根据伤病、负荷比、睡眠、疲劳、疼痛/RPE 计算最高强度，再验证模型 JSON 的星期覆盖、训练日数、动作强度和证据 ID；失败不落库。

## 11. 如何保证计划中的 RAG 证据没有幻觉？

RAG 服务返回本次可用 evidence id 列表，模型 prompt 限制只能引用该列表，服务层二次验证 `evidence_ids` 是其子集。模型给出任意其他 ID 就报错并不创建计划。

## 12. Coros MCP 为什么要串行化？

stdio MCP 是共享的一对输入输出流。多个请求交叉发送会造成回包顺序和协议状态污染，因此锁住完整“发送—等待匹配回包”过程。超时后直接销毁该流，下一次新建进程，不继续消费可能迟到的旧回包。

社区 MCP 依赖 FastMCP，可能与 FastAPI 的 Web 依赖版本冲突，因此把它固定到独立 `.tools` 虚拟环境，只通过 stdio JSON-RPC 通信；服务端还强制 `readonly` 工具集并隐藏认证工具。这样 Agent 既拿不到账号令牌，也无法调用社区 MCP 的写入类能力。

## 13. Windows 上为什么不使用 select 读取 subprocess stdout？

`select.select` 在 Windows 不支持普通管道句柄。这里用 daemon reader thread 把 `readline` 结果放进 queue，主线程按 timeout 等待；超时后终止子进程。这一实现也便于单测超时重置。

## 14. 为什么活动唯一键不能用日期？

同一天可能有晨跑和夜跑。旧 `(user_id, date, data_type)` 唯一键会覆盖其中一条。新的活动优先使用 Coros 外部 activity id，缺失时用稳定字段哈希；日指标和睡眠仍按日期幂等。

## 15. 如何测试没有真实 LLM 或 Coros 的部分？

FastAPI 通过依赖覆盖替换 Agent/Coros；训练计划服务的安全策略和 schema 校验是纯业务逻辑，可直接构造画像、快照、反馈和计划；Coros client 注入 fake process，模拟 JSON-RPC 握手、回包和阻塞超时。

## 16. 目前有哪些真实不足？

路由已使用结构化 LLM 分类，但分类质量仍需离线评测和线上观测；查询规划触发与当前重排仍主要是受控规则/词法策略，不是 Cross-Encoder 语义精排；聊天文本的 `[证据:N]` 尚未做生成后白名单校验。计划生成的质量还没有人工偏好/忠实度评测；Coros 已完成真实账号认证、端到端同步和 external key 去重检查，但尚未有长期失败率、延迟和重试策略的线上观测；Qdrant 是单节点演示。这些会按真实问题和评测结果再演进，而不是直接堆 cross-encoder、多 Agent 或设备自动下发。

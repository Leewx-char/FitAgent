| 2. 数据修复 | 活动从日期级唯一键改为 external id；迁移兼容 MySQL 外键 | 同一天两个 Coros 活动均能保留；迁移可升级 | 已完成 |

## 当前发现与对应决策

1. **记忆不是“加载更多聊天记录”**：旧方案将 20 轮原文全部放入 prompt，且事实提取会读取 assistant 消息。现在保留原文审计，但把 prompt 限为最近 10 轮（20 条）消息；较早状态可重建，长期信息必须经用户确认。
2. **MCP 不是可靠性方案本身**：旧 Coros stdio client 在 Windows 上使用 `select.select`，并发请求会共享一条无序流。现在把协议串行、超时、重启和生命周期放在 adapter 内。
3. **训练计划不是一段 prompt**：为了可测与可解释，先由代码给出安全上限，再让模型填充受 schema 限制的计划；RAG 证据 ID 也在服务端闭环校验。
4. **数据层的唯一键就是产品规则**：日期级唯一键隐含“一天仅一项活动”的错误假设，已替换为外部记录 ID。

## 下一轮建议（不宣称已完成）

1. 将 Coros 同步改为可观测任务（记录每个 source 的耗时、返回量与错误类型），再基于真实失败率决定是否需要队列或重试机制；当前同步保持用户显式触发，避免后台静默刷新设备数据。
2. 建立 20–30 条“个人化建议/训练计划”评测集：包括来源是否忠实、强度是否符合策略、伤病/疲劳场景是否正确降级、记忆是否仅取 confirmed 项。
3. 基于真实轨迹数据决定是否引入 LLM schema 摘要或 cross-encoder rerank；不先行堆叠多 Agent。
4. 若产品需要官方 COROS MCP，则新增 OAuth + streamable HTTP adapter，并保留当前本地 stdio adapter 作为可测试接口；不可把两种 transport 混在同一实现中。
